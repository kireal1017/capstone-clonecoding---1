# 프론트엔드 PRD - 세션별 개발 문서 v2

> 대상 프로젝트: 스마트 점검 리포트  
> 개발 방식: OMC + Claude Code 세션 분할 개발  
> 프론트엔드 기술 스택: Vue 3 + Vite + Tailwind CSS  
> 핵심 보강사항: 프론트엔드 UI는 반드시 와이어프레임을 기준으로 구현한다.

---

## 1. 프론트엔드 목표

Vue 3 + Vite + Tailwind CSS를 사용하여 스마트 점검 리포트의 역할별 화면과 점검 작성 플로우를 구현한다.

프론트엔드는 API 서버와 통신하여 실제 SQLite 데이터를 조회/저장하고, GPT API 결과를 백엔드를 통해 받아 화면에 JSON 카드 형태로 표시한다.

프론트엔드 구현은 단순 CRUD 화면이 아니라, 기존에 작성한 전체 유스케이스 와이어프레임을 기준으로 한 **모바일 우선 카드형 UX**를 따라야 한다.

---

## 2. 기술 기준

| 항목 | 내용 |
|---|---|
| Framework | Vue 3 |
| Build Tool | Vite |
| CSS | Tailwind CSS |
| Router | Vue Router |
| 상태 관리 | 우선 Vue ref/reactive 또는 Pinia 중 프로젝트 상황에 맞게 결정 |
| API 통신 | fetch 또는 axios |
| 인증 | 로그인 없음, localStorage 기반 selectedUser |
| PDF | `/reports/:id/print` 또는 인쇄용 템플릿에서 `window.print()` |
| 이미지 | 파일 선택 → Base64 변환 → API 전송 |
| UI 기준 | 와이어프레임 기반 모바일 우선 카드형 UI |

## 3. 와이어프레임 기반 구현 기준

### 3.1 필수 참조 와이어프레임

프론트엔드 구현은 반드시 아래 와이어프레임의 화면 흐름과 UI 구조를 기준으로 한다.

| 구분 | 참조 문서 |
|---|---|
| 전체 유스케이스 와이어프레임 | `docs/wireframes/스마트점검리포트_전체유스케이스_와이어프레임_v6.html` |
| 적용 대상 | 시공업자, 임대인, 임차인, 공유 링크 접근, 리포트 양식 |
| 구현 기준 | 화면 순서, 카드 배치, 주요 버튼, 입력 흐름, 리포트 구조 |

Claude Code 세션에서 해당 HTML 파일이 실제 프로젝트에 존재하지 않는 경우, 본 프론트엔드 PRD의 와이어프레임 구현 기준을 우선하여 동일한 구조로 구현한다.

---

### 3.2 와이어프레임 적용 원칙

프론트엔드는 단순 CRUD 화면이 아니라, 와이어프레임에서 정리한 **모바일 우선 카드형 UX**를 기준으로 구현한다.

| 항목 | 구현 기준 |
|---|---|
| 기본 레이아웃 | 모바일 우선 반응형 카드 UI |
| PC 레이아웃 | 모바일 흐름을 유지하되 넓은 화면에서는 목록/상세/비교를 2열 이상으로 확장 가능 |
| 화면 스타일 | Tailwind CSS 기반의 깔끔한 카드, 태그, 상태 배지, 하단 액션 버튼 |
| 데이터 입력 | 한 화면에 모든 기능을 몰아넣지 않고, 와이어프레임 순서에 맞춘 단계형 입력 |
| AI 결과 | 긴 설명문이 아니라 행동 카드 형태로 표시 |
| 리포트 | 웹 조회와 PDF 출력을 모두 고려한 HTML 템플릿 구조 |
| 생성 완료 리포트 | 수정/삭제 UI를 절대 표시하지 않음 |
| 공유 링크 화면 | 조회와 PDF 저장만 제공, 확인 완료/수정/삭제 제공 금지 |

---

### 3.3 실제 구현 시 주의사항

와이어프레임 HTML은 설명용으로 작성된 저충실도 화면이다. 실제 구현에서는 다음 기준을 따른다.

1. **핸드폰 프레임 자체는 구현하지 않는다.**  
   와이어프레임의 검은 휴대폰 외곽선은 설명용이다. 실제 앱은 일반 반응형 웹 화면으로 구현한다.

2. **화면 순서와 정보 구조는 유지한다.**  
   카드의 정확한 픽셀 크기보다 사용자 흐름, 정보 순서, 버튼 위치, 입력 방식이 더 중요하다.

3. **모바일에서는 한 화면 한 작업 원칙을 우선한다.**  
   점검 목적 선택, 대상 입력, 전체 점검, 문제 항목 점검, AI 도우미, 의견 작성, 제출 검토가 자연스럽게 이어져야 한다.

4. **PC에서는 사용성을 위해 확장 가능하다.**  
   목록 + 상세, 이전 리포트 + 현재 리포트 비교처럼 PC에서 유리한 화면은 2열 레이아웃으로 구성할 수 있다.

5. **AI 점검 도우미는 반드시 행동형 카드로 구현한다.**  
   `촬영`, `확인`, `참고`, `초안 적용` 같은 버튼 또는 액션을 포함해야 한다.

6. **리포트 양식은 별도 출력용 템플릿으로 구현한다.**  
   화면용 버튼과 내비게이션은 `@media print`에서 제외한다.

### 3.5 시공업자 화면 구현 기준

시공업자 화면은 다음 순서를 따른다.

```text
시공업자 홈
→ 새 점검 시작
→ 점검 목적 선택
→ 점검 대상 입력
→ 전체 점검 또는 문제 항목 점검
→ AI 점검 도우미
→ 사진 첨부
→ 전문 의견 작성
→ 점검 제출
→ 리포트 자동 생성
```

#### 시공업자 홈

| UI 요소 | 구현 기준 |
|---|---|
| 새 점검 시작 버튼 | 가장 눈에 잘 보이는 Primary Button |
| 작성 중 점검 카드 | draft 상태 점검 표시 |
| 제출 대기 점검 카드 | submitted 상태 점검 표시 |
| 상태 태그 | 점검 유형, 상태, 호실 표시 |
| 하단 또는 상단 내비게이션 | 홈, 점검, 기록 접근 |

#### 점검 목적 선택

| UI 요소 | 구현 기준 |
|---|---|
| 점검 유형 카드 | 입주 전, 정기, 퇴거 전, 퇴거 후, 긴급, 수리 전, 수리 후 |
| 설명 문구 | 각 점검 유형의 목적을 1줄로 표시 |
| 선택 상태 | 선택된 카드는 테두리/체크 표시 |
| 다음 버튼 | 선택 후 점검 대상 입력으로 이동 |

#### 점검 대상 입력

| UI 요소 | 구현 기준 |
|---|---|
| 건물/호실 선택 | seed DB의 호실 목록 기반 선택 |
| 점검일 | 기본값 오늘 날짜 |
| 임대인/임차인 | 선택 호실 기준 자동 표시 |
| 진행 방식 표시 | 입주 전/정기 = 전체 점검, 나머지 = 문제 항목 점검 |

### 3.6 전체 점검 화면 구현 기준

전체 점검은 입주 전 점검과 정기 점검에 적용한다.

```text
공간별 빠른 체크
→ 주의/수리 필요 항목만 상세 입력
→ AI 점검 도우미
→ 사진 첨부
→ 최종 의견
→ 제출
```

#### 공간별 빠른 체크

| 공간 | 기본 항목 |
|---|---|
| 현관 | 현관문, 도어락, 문틀, 신발장 |
| 거실 | 벽지, 바닥, 창호, 콘센트 |
| 주방 | 싱크대, 수전, 배수, 후드 |
| 방1 | 벽지, 바닥, 창호, 콘센트 |
| 방2 | 벽지, 바닥, 창호, 콘센트 |
| 화장실 | 세면대, 변기, 수전, 배수 |
| 베란다 | 창호, 바닥, 배수, 누수 흔적 |
| 보일러룸 | 보일러, 배관, 밸브, 누수 흔적 |

각 공간은 카드 형태로 표시하고, 상태값은 다음 3개 버튼으로 제공한다.

```text
정상 / 주의 / 수리 필요
```

#### 이상 항목 상세 기록

주의 또는 수리 필요로 선택된 항목만 상세 입력 대상으로 표시한다.

| 입력 항목 | 설명 |
|---|---|
| 공간 | 자동 표시 |
| 세부 항목 | 선택 또는 입력 |
| 위치 | 구체 위치 입력 |
| 상태 설명 | 텍스트 입력 |
| 사진 | PhotoUploader 연결 |
| 사진 설명 | 선택 입력 |

### 3.7 문제 항목 점검 화면 구현 기준

문제 항목 점검은 퇴거 전, 퇴거 후, 긴급, 수리 전, 수리 후 점검에 적용한다.

```text
분야/문제 항목 선택
→ 위치와 증상 설명 입력
→ 현장 확인 항목 선택
→ AI 점검 도우미
→ 사진 첨부
→ 전문 의견 작성
→ 제출
```

#### 문제 분야

| 분야 | 대표 문제 항목 |
|---|---|
| 인테리어·마감 | 벽지 찢어짐, 벽지 오염, 바닥 찍힘, 몰딩 파손, 타일 균열 |
| 샷시·창호 | 방충망 찢어짐, 창문 작동 불량, 유리 파손, 실리콘 들뜸, 잠금장치 불량 |
| 설비·배관 | 누수, 배수 불량, 수전 흔들림, 보일러 이상, 배관 부식 |
| 전기 | 콘센트 불량, 조명 미작동, 스위치 불량, 차단기 이상, 배선 노출 |
| 소방·안전 | 감지기 미작동, 소화기 미비, 가스누설 의심, 비상등 불량, 안전 위험 요소 |

#### 현장 확인 항목

현장 확인 항목은 시공업자가 직접 선택한다. AI가 자동으로 선택하지 않는다.

```text
있음 / 없음 / 확인 필요
```

### 3.8 AI 점검 도우미 UI 구현 기준

AI 점검 도우미는 와이어프레임처럼 **행동형 카드 UI**로 구현한다.

#### 입력

AI 요청에는 다음 데이터를 포함한다.

| 데이터 | 설명 |
|---|---|
| 점검 유형 | 입주 전, 정기, 긴급 등 |
| 점검 흐름 | whole 또는 issue |
| 공간/분야 | 거실, 설비·배관 등 |
| 문제 항목 | 누수, 벽지 찢어짐 등 |
| 위치 | 세부 위치 |
| 증상 설명 | 시공업자 입력 텍스트 |
| 현장 확인 항목 | 있음/없음/확인 필요 선택값 |
| 현재 첨부 사진 수 | 사진 누락 판단용 |

#### 출력 UI

| JSON 필드 | 화면 표시 |
|---|---|
| `summary` | 상단 요약 카드 |
| `actionCards` | 촬영/확인/참고 버튼이 있는 행동 카드 |
| `requiredDocuments` | 필요 자료 태그 또는 체크리스트 |
| `cautionPhrases` | 표현 주의 안내 카드 |
| `opinionDraft` | 전문 의견 초안 카드 및 초안 적용 버튼 |

#### 금지

- AI 결과를 긴 문단만으로 표시하지 않는다.
- 법적 책임 판단처럼 보이는 UI 라벨을 사용하지 않는다.
- `임차인 책임`, `임대인 책임`, `보증금 공제 가능` 같은 문구를 강조 표시하지 않는다.
- AI 초안을 리포트에 직접 표시하지 않고, 시공업자 최종 의견으로 수정된 값만 리포트에 반영한다.

### 3.9 리포트 UI 구현 기준

리포트 화면은 웹 조회와 PDF 출력을 모두 고려한다.

#### 리포트 상세 화면

| 영역 | 구현 기준 |
|---|---|
| 기본 정보 | 건물명, 호실, 점검 유형, 점검일, 생성일 |
| 참여자 | 시공업자, 임대인, 임차인 |
| 등급 | 규칙 기반 산출 등급 표시 |
| 점검 요약 | 공간 수, 상세 기록 수, 이미지 수 |
| 체크리스트 결과 | 공간/항목/상태/위치/설명 |
| 사진 증빙 | 항목별 이미지와 설명 |
| 시공업자 의견 | 최종 의견만 표시 |
| 확인 상태 | 임대인/임차인 확인 여부 |
| 주의 문구 | 법적 책임 판단이 아님을 명시 |

#### 인쇄용 템플릿

`PrintableReportTemplate`은 `/reports/:id/print`에서 사용한다.

PDF 출력 시 제외해야 하는 요소:

- 수정 버튼
- 삭제 버튼
- 공유 버튼
- 확인 완료 버튼
- 내비게이션
- 입력 폼
- 화면용 필터

### 3.10 임대인/임차인 UI 구현 기준

#### 임대인

| 화면 | 구현 기준 |
|---|---|
