## 0. 전체 흐름 다이어그램

```
[비로그인 사용자]
      │
      ├─ /login 접근 ──────────────────────────────┐
      │        │                                   │
      │   로그인 성공                          회원가입 클릭
      │        │                                   │
      │        ▼                              /auth (회원가입)
      │   [Access Token 저장]                      │
      │   [Refresh Token 쿠키]               가입 성공
      │        │                                   │
      │        ▼                              /login 리다이렉트
      └───► / (메인) ◄──────────────────────────────┘
                │
                ├─ FAB(+) 클릭 ──► /plans/new ──► 저장 성공 ──► /
                │
                ├─ 일정 카드 클릭 ──► /?planId=X (상세 모달)
                │                          │
                │                   수정 / 삭제 / 완료 토글
                │                          │
                │                     모달 닫기 ──► /
                │
                ├─ 프로필 아이콘 ──► /profile
                │                      │
                │               닉네임/비번/아바타 변경
                │               카테고리 추가/수정/삭제
                │                      │
                │                  저장 후 ──► /profile 유지
                │
                └─ 로그아웃 ──► /login
```

## 1. 비로그인 사용자 진입 흐름

### 1-1. 보호된 경로 접근 (인증 가드)

[PRD 확정] PRD §6 Protected Route 동작

| 단계 | 동작 |
|---|---|
| 1 | 사용자가 `/`, `/plans/new`, `/profile` 등 보호 경로 접근 |
| 2 | `PrivateRoute` 컴포넌트가 `authStore.accessToken` 확인 |
| 3 | 없으면 현재 경로를 `location.state.from`에 저장 |
| 4 | `/login`으로 리다이렉트 |
| 5 | 로그인 성공 후 `location.state.from`으로 복귀 (없으면 `/`) |

**이미 로그인한 사용자의 `/login`, `/auth` 접근:**
- `PrivateRoute` 반대 가드: `accessToken` 있으면 `/`로 리다이렉트

---

### 1-2. 회원가입 흐름

[PRD 확정] PRD §10-1, §12-1, K-02=B

| 단계 | 화면 | 동작 |
|---|---|---|
| 1 | `/login` | "회원가입" 링크 클릭 → `/auth`로 이동 |
| 2 | `/auth` | 닉네임·이메일·비밀번호·비밀번호 확인 입력 |
| 3 | `/auth` | 각 필드 blur 시 Zod 즉시 검증 → 인라인 오류 표시 |
| 4 | `/auth` | "가입하기" 버튼 클릭 → 전체 폼 Zod 검증 |
| 5 | `/auth` | 검증 통과 → `POST /api/v1/auth/register` |
| 6 | 서버 | users INSERT + categories 5개 시드 INSERT (트랜잭션) |
| 7 | `/auth` → `/login` | 201 응답 → `/login`으로 리다이렉트 |
| 8 | `/login` | 회원가입 완료 토스트 표시 [AI 제안안] |

**오류 처리:**
- 이메일 중복(409): `email` 필드 인라인 오류 "이미 사용 중인 이메일입니다."
- 검증 실패(422): 해당 필드 인라인 오류
- 서버 오류(500): 상단 토스트 "일시적인 오류가 발생했습니다."

---

### 1-3. 로그인 흐름

[PRD 확정] PRD §10-1, §12-2

| 단계 | 화면 | 동작 |
|---|---|---|
| 1 | `/login` | 이메일·비밀번호 입력 |
| 2 | `/login` | "로그인" 버튼 클릭 → `POST /api/v1/auth/login` |
| 3 | 클라이언트 | 200 응답 → `accessToken`을 `authStore`에 저장 |
| 4 | 클라이언트 | `refresh_token` httpOnly 쿠키 자동 설정 (서버 `Set-Cookie`) |
| 5 | `/login` → `/` | `location.state.from` 또는 `/`로 리다이렉트 |

**오류 처리:**
- 인증 실패(401): 비밀번호 필드 하단 인라인 오류 "이메일 또는 비밀번호가 올바르지 않습니다."
- Rate Limit(429): 토스트 "요청이 너무 많습니다. 잠시 후 다시 시도하세요."

## 2. 인증된 사용자 — 메인 페이지 진입 흐름

[PRD 확정] PRD §10-2, K-05=B

| 단계 | 동작 |
|---|---|
| 1 | `/` 접근 → `PrivateRoute` 통과 |
| 2 | `MainPage` 마운트 → TanStack Query 병렬 요청 시작 |
| 3 | `GET /api/v1/plans?month=YYYY-MM` — 현재 월 일정 로드 |
| 4 | `GET /api/v1/categories` — 카테고리 목록 로드 |
| 5 | `GET /api/v1/auth/me` — 프로필(아바타) 로드 [AI 제안안] |
| 6 | 로딩 완료 → 순서대로 렌더링: 캘린더 → 주간 바 → 오늘 할 일 (K-05=B) |
| 7 | `display_date == 오늘(KST)` 인 일정만 오늘 할 일에 표시 (K-10=B) |
| 8 | 오늘 할 일 정렬: 완료 미완료 우선 → 중요도(high→normal→low) → due_time 빠른 순 → **4순위: created_at ASC (등록 순서, PRD §22-2)** (K-04=A, FE-04) |
| 9 | **정렬은 서버 ORDER BY로 수행. 클라이언트 추가 정렬 없음.** (FE-04) |

**`?planId` 쿼리 파라미터 처리:**
- `MainPage` 마운트 시 `useSearchParams`로 `planId` 감지
- `planId` 존재 시 `GET /api/v1/plans/:id` 호출 → `PlanDetailModal` 자동 오픈

## 3. 일정 등록 흐름

[PRD 확정] PRD §10-3, §12-3, §26

| 단계 | 화면 | 동작 |
|---|---|---|
| 1 | `/` | 우측 하단 FAB(`+`) 클릭 → `/plans/new`로 이동 |
| 2 | `/plans/new` | 폼 필드 입력: 제목, 마감일, 마감시간, 처리날짜, 카테고리, 중요도, 메모, 알림 |
| 3 | `/plans/new` | 마감일 선택 시 `displayDate` 자동으로 동일 날짜로 설정 (K-10=B) |
| 4 | `/plans/new` | "저장하기" 클릭 → Zod 전체 검증 |
| 5 | `/plans/new` | 검증 실패 → 인라인 오류 표시, 저장 중단 |
| 6 | `/plans/new` | 검증 통과 → 저장 확인 모달 "이 일정을 등록하시겠습니까?" |
| 7 | 저장 확인 모달 | "확인" 클릭 → `POST /api/v1/plans` |
| 8 | 클라이언트 | 201 성공 → `invalidateQueries(['plans'])` |
| 9 | 클라이언트 | `/`로 리다이렉트, 갱신된 오늘 할 일 목록 표시 |
| 10 | 저장 확인 모달 | "취소" 클릭 → 모달 닫기, 폼 유지 |

**취소 흐름:**
- "취소" 버튼 클릭 → 취소 확인 모달 "작성 중인 내용이 사라집니다. 취소하시겠습니까?"
- 확인 → `/`로 리다이렉트, 입력 내용 파기
- 취소 → 모달 닫기, 폼 유지

**[FE-06] 헤더 ← 뒤로가기 동작 확정:**
- 헤더 `←` 아이콘 클릭 = 취소 버튼과 동일 → 취소 확인 모달 트리거
- 폼 입력 내용이 없는 초기 상태에서 `←` 클릭 → 모달 없이 바로 `/`로 이동
- React Router v6 `useBlocker` 훅으로 폼 내용 있을 때 네비게이션 차단
- 브라우저 백 버튼(popstate) 및 새로고침 시 `beforeunload` 이벤트 처리

## 4. 일정 상세 확인 흐름 (K-08=B 모달)

[PRD 확정] PRD §12-4, §27, K-08=B

### 4-1. 진입 경로

| 진입 위치 | 동작 |
|---|---|
| 오늘 할 일 카드 클릭 | `navigate('/?planId=<id>')` |

| 캘린더 날짜 셀 클릭 | 해당 날짜 일정 목록 표시 → 일정 클릭 → `navigate('/?planId=<id>')` |

| 3 | 성공 → `PlanDetailModal` 렌더링 (뷰 모드) |
| 4 | 실패(404/403) → 오류 토스트, `planId` 쿼리 파라미터 제거 |

|---|---|

| ESC 키 | 동일 |
| 오버레이 클릭 | [PRD 확정] PRD §13-6 — 오버레이 클릭 시 닫힘 |

## 5. 일정 수정 흐름

[PRD 확정] PRD §12-5, §28

| 단계 | 화면 | 동작 |
|---|---|---|
| 1 | 상세 모달 (뷰 모드) | "수정" 버튼 클릭 → 모달 내 편집 모드로 인라인 전환 |
| 2 | 상세 모달 (편집 모드) | title, due_date, due_time, display_date, category_id, priority, memo, is_remind 수정 가능 |
| 3 | 상세 모달 (편집 모드) | "저장" 클릭 → Zod 검증 |
| 4 | 상세 모달 | 검증 통과 → 저장 확인 모달 |
| 5 | 저장 확인 모달 | "확인" → `PATCH /api/v1/plans/:id` (변경 필드만) |
| 6 | 클라이언트 | 성공 → `invalidateQueries(['plans'])` + 뷰 모드로 복귀 |

**[FE-10] 수정 모드 display_date 연동 정책 확정:**
- 수정 모드에서 `due_date` 변경 시 `display_date` **자동 연동 없음**. 기존 값 유지.
- 사용자가 명시적으로 처리 날짜 필드를 직접 변경했을 때만 적용.
- 등록 모드(PlanCreatePage)에서만 `due_date` 변경 시 `display_date` 자동 동일 설정 (K-10=B).

**취소 흐름:**
- 편집 모드 "취소" 클릭 → 취소 확인 모달
- 확인 → 편집 내용 파기, 뷰 모드로 복귀

## 6. 일정 삭제 흐름

[PRD 확정] PRD §12-6, §29

| 단계 | 화면 | 동작 |
|---|---|---|
| 1 | 상세 모달 | "삭제" 버튼 클릭 |
| 2 | 삭제 확인 모달 | "이 일정을 삭제하시겠습니까? 이 작업은 되돌릴 수 없습니다." |

- 네트워크 오류: 오류 토스트, 삭제 확인 모달 유지

## 8. 검색 흐름

[PRD 확정] PRD §30-1

| 단계 | 화면 | 동작 |
|---|---|---|
| 1 | 메인 헤더 | 검색바에 키워드 입력 |
| 2 | 클라이언트 | debounce 300ms 후 `planStore.searchKeyword` 업데이트 |
| 3 | 클라이언트 | TanStack Query queryKey 갱신: `['plans', 'list', { search: keyword }]` |
| 4 | 클라이언트 | `GET /api/v1/plans?search=<keyword>` 자동 요청 |
| 5 | 메인 페이지 | 결과 표시: title/memo에 keyword 포함된 일정만 표시 |
| 6 | 검색 결과 없음 | "검색 결과가 없습니다. 다른 키워드로 검색해보세요." |
| 7 | 검색어 지우기 | 빈 문자열 → 전체 일정 목록으로 복귀 |

**[FE-03] 검색 결과 표시 영역 확정 (PRD §30-1 D-11 미확정 → AI 권장안 채택):**
- 검색 모드 진입 시(`searchKeyword !== ''`): `<MonthlyCalendar />` 및 `<WeeklyPlanBar />` **숨김**
- 전체 미삭제 레코드 대상 검색 (현재 조회 월 한정 없음)
- `<SearchResultList />` 별도 영역에 전체 검색 결과 일정 목록 표시
- `<TodayPlanList />` 섹션은 검색 모드에서도 유지 (검색 결과 섹션과 별개)
- 검색어 지우기 시: 검색 모드 해제, 캘린더·주간바 복귀

### 10-2. 비밀번호 변경

### 10-3. 아바타 업로드

| 단계 | 동작 |
|---|---|
| 1 | `/profile` — 아바타 이미지 또는 "프로필 이미지 변경" 버튼 클릭 |
| 2 | 파일 선택 다이얼로그 열림 (accept: image/jpeg, image/png, image/webp) |

## 15. 주간 일정 바 인터랙션 흐름

[PRD 확정] PRD §24, K-05=B

| 단계 | 동작 |
|---|---|
| 1 | 이번 주(월~일) 각 요일의 일정 개수를 막대 높이로 표현 |
| 2 | 오늘 요일 강조 (charcoal 색상 바) |
| 3 | 요일 클릭 → `calendarStore.expandedWeekDay` 해당 요일로 설정 |
| 4 | 클릭된 요일 아래로 일정 카드 목록 확장 표시 |
| 5 | 이미 선택된 요일 재클릭 → `expandedWeekDay = null` → 접힘 |
| 6 | 다른 요일 클릭 → 이전 확장 닫히고 새 요일 확장 |
| 7 | 확장 목록의 일정 **카드 본문 클릭** → `navigate('/?planId=<id>')` (상세 모달 **뷰 모드** 진입) |
| 8 | 확장 목록의 일정 카드 **연필 아이콘(✏) 클릭** → `navigate('/?planId=<id>&edit=1')` 또는 상세 모달 오픈 후 즉시 편집 모드 진입 (PRD §24-3, FE-11) |

**[FE-11] 주간 바 확장 카드 연필 아이콘 확정 (PRD §24-3 준수):**
- PRD §24-3에 연필 아이콘이 명시됨 → 와이어프레임 및 화면 흐름에 반영
- 카드 본문 클릭: 상세 모달 **뷰 모드**로 진입
- 연필 아이콘 클릭: 상세 모달 + **편집 모드**로 직접 진입 (뷰 모드 경유 없음)
- 두 인터랙션이 명확히 분리됨
