## 1. 추천 기술 스택 후보

### 1-1. 프론트엔드 기반 `[명세서 확정]`

- 제안: React 18 + TypeScript + TailwindCSS v3
- 이유: 기능명세서에 확정된 스택이며, React 18의 Concurrent 기능과 TypeScript의 타입 안전성은 캘린더·할 일 관리처럼 복잡한 상태를 다루는 UI에 적합하다.
- 대안: 없음 (명세서 확정)
- 추천 여부: 강력 추천
- 사용자 확인 필요 여부: 불필요

### 1-2. 백엔드 기반 `[명세서 확정]`

- 제안: Node.js + TypeScript
- 이유: 기능명세서에 확정된 스택이며, 프론트엔드와 언어를 통일해 타입 공유(zod 스키마 등)가 가능하다.
- 대안: 없음 (명세서 확정)
- 추천 여부: 강력 추천
- 사용자 확인 필요 여부: 불필요

### 1-3. 데이터베이스 `[명세서 확정]`

- 제안: SQLite
- 이유: 기능명세서에 확정된 DB이며, 단일 파일 기반으로 로컬·개발 환경에서 설정 비용이 없다.
- 대안: 없음 (명세서 확정)
- 추천 여부: 강력 추천
- 사용자 확인 필요 여부: 불필요

### 1-4. 백엔드 프레임워크 `[AI 제안안]`

- 제안: Express.js (with express-async-errors)
- 이유: 생태계가 가장 넓고 레퍼런스·미들웨어가 풍부하여 학습 비용이 낮다. 소규모 프로젝트에서 Fastify나 Hono 대비 오버헤드가 없다.
- 대안: (A) Fastify — 성능 우위, 플러그인 시스템 체계적 / (B) Hono — 초경량, Edge 호환
- 추천 여부: 추천
- 사용자 확인 필요 여부: 권장

### 1-5. ORM / DB 접근 `[AI 제안안]`

- 제안: Prisma (SQLite 어댑터)
- 이유: 타입 안전 쿼리 빌더와 자동 마이그레이션을 제공해 TypeScript 프로젝트에서 생산성이 높다.
- 대안: (A) Drizzle ORM — 경량, SQL에 가까운 문법 / (B) better-sqlite3 raw — 의존성 최소, 학습 부담
- 추천 여부: 추천
- 사용자 확인 필요 여부: 권장

### 1-6. 프론트엔드 빌드 도구 `[AI 제안안]`

- 제안: Vite
- 이유: HMR이 빠르고 설정이 단순하다. CRA(Create React App)는 2023년 이후 유지보수가 중단되었다.
- 대안: (A) CRA — 설정 없음, 하지만 deprecated / (B) Next.js — SSR 필요 시, 단 이 서비스는 SPA로 충분
- 추천 여부: 강력 추천
- 사용자 확인 필요 여부: 불필요

### 1-7. 상태 관리 `[AI 제안안]`

- 제안: TanStack Query v5 (서버 상태) + Zustand (클라이언트 상태)
- 이유: 서버 데이터(일정, 카테고리)는 TanStack Query로 캐싱·동기화하고, UI 전역 상태(모달 열림, 선택된 날짜)는 Zustand로 가볍게 관리하는 패턴이 현대 React 프로젝트 표준에 가깝다.
- 대안: (A) Redux Toolkit + RTK Query — 엔터프라이즈 수준, 이 프로젝트엔 과함 / (B) React Context + useState — 단순하지만 리렌더링 최적화 어려움
- 추천 여부: 추천
- 사용자 확인 필요 여부: 권장

### 1-8. 라우터 `[AI 제안안]`

- 제안: React Router v6
- 이유: 레퍼런스가 가장 많고 파일 기반 라우팅 없이 선언적 라우팅을 지원한다.
- 대안: TanStack Router — 타입 안전 경로, 하지만 러닝 커브 있음
- 추천 여부: 추천
- 사용자 확인 필요 여부: 불필요

### 1-9. 폼 관리 `[AI 제안안]`

- 제안: React Hook Form + Zod (resolver 연결)
- 이유: 일정 등록/수정 폼이 핵심 기능이며, uncontrolled 방식으로 렌더링 최소화, zod 스키마 재사용 가능.
- 대안: Formik + yup — 오래된 대안, 성능 열세
- 추천 여부: 강력 추천
- 사용자 확인 필요 여부: 불필요

### 1-10. 날짜 유틸리티 `[AI 제안안]`

- 제안: date-fns v3
- 이유: 트리쉐이킹 친화적이고 모듈식 API가 TypeScript와 잘 맞는다. dayjs보다 번들 사이즈가 예측 가능하다.
- 대안: dayjs + timezone 플러그인 — 더 작은 기본 번들, 플러그인 체인 필요

- 사용자 확인 필요 여부: 불필요

### 1-11. 테스트 `[AI 제안안]`

- 제안: Vitest + React Testing Library (단위/통합) + Playwright (E2E)
- 이유: Vitest는 Vite 환경에서 Jest 대비 빠르며, RTL은 사용자 관점 테스트 표준이다.

## 2. 프론트엔드 구조 제안

### 2-1. 폴더 구조 `[AI 제안안]`

- 제안: feature 슬라이스 기반 구조 (`src/features/`, `src/pages/`, `src/components/`, `src/api/`, `src/hooks/`, `src/types/`, `src/utils/`, `src/styles/`)
- 이유: 기능별로 파일을 모아두면 일정(plans), 카테고리(categories), 인증(auth) 각 도메인이 독립적으로 성장할 수 있다.
- 대안: 전통적 계층 구조 (`components/`, `pages/`, `services/`) — 단순하지만 파일이 분산됨
- 추천 여부: 추천
- 사용자 확인 필요 여부: 불필요

### 2-2. 라우팅 전략 `[AI 제안안]`

- 제안: SPA + Protected Routes (인증 필요 경로는 PrivateRoute 컴포넌트로 가드, 미인증 시 `/login` 리디렉션)
- 이유: 다중 사용자 구조(K-01=A 선택 기준)에서 인증 없는 접근을 클라이언트 수준에서 1차 차단한다. 서버 API에서 2차 검증.
- 대안: 없음 (다중 사용자 채택 시 필수)
- 추천 여부: 강력 추천
- 사용자 확인 필요 여부: 불필요 (K-01 결정 후 자동 결정)

### 2-3. 상태 관리 분리 `[AI 제안안]`

- 제안: 서버 상태는 TanStack Query(캐시·갱신·로딩), 클라이언트 UI 상태는 Zustand(선택된 날짜, 모달 열림 여부, 검색 키워드)
- 이유: 두 관심사를 분리하면 각각 최적화된 도구를 쓸 수 있고, 컴포넌트 복잡도가 낮아진다.
- 대안: 모든 상태를 useState + prop drilling — 소규모 시 가능하지만 캘린더·모달 연동 시 복잡
- 추천 여부: 추천
- 사용자 확인 필요 여부: 불필요

### 2-4. 컴포넌트 설계 원칙 `[AI 제안안]`

- 제안: Atomic Design의 가벼운 적용 — UI 원자(Button, Input, Chip, Checkbox, Badge)는 `src/components/ui/`에, 도메인 복합 컴포넌트(PlanCard, CategoryChip, CalendarCell)는 `src/features/<domain>/components/`에
- 이유: 과도한 atomic 계층 없이도 재사용성과 도메인 응집도를 균형 있게 유지한다.
- 대안: 단일 `components/` 폴더 — 단순하지만 파일이 많아지면 혼잡
- 추천 여부: 추천
- 사용자 확인 필요 여부: 불필요

## 3. 백엔드 구조 제안

### 3-1. 레이어드 아키텍처 `[AI 제안안]`

- 제안: 4계층 — `routes` → `controllers` → `services` → `repositories` (+ `db` 연결 레이어)
- 이유: 각 계층이 한 가지 역할만 담당해 테스트와 유지보수가 쉽다. SQLite + Prisma 조합에서 repository 패턴이 쿼리 로직을 service에서 분리한다.
- 대안: 2계층(routes → services, repository 생략) — 단순하지만 테스트 시 DB 의존성 직접 노출
- 추천 여부: 추천
- 사용자 확인 필요 여부: 불필요

### 3-2. 폴더 구조 `[AI 제안안]`

- 제안: `src/routes/`, `src/controllers/`, `src/services/`, `src/repositories/`, `src/middlewares/`, `src/utils/`, `src/types/`, `prisma/` (스키마 및 마이그레이션)
- 이유: 도메인별(auth, plans, categories, profile) 파일을 각 계층 폴더 아래에 두면 탐색이 직관적이다.
- 대안: 도메인별 폴더(`src/auth/`, `src/plans/`) — 도메인이 많을수록 유리하나 이 규모에선 과함
- 추천 여부: 추천
- 사용자 확인 필요 여부: 불필요

### 3-3. 미들웨어 구성 `[AI 제안안]`

- 제안: `authMiddleware` (JWT 검증), `errorHandler` (전역 에러 포맷), `validate` (zod 스키마 검증), `requestLogger` (morgan 또는 직접 구현)
- 이유: 공통 관심사를 미들웨어로 분리해 컨트롤러를 비즈니스 로직에만 집중시킨다.
- 대안: 컨트롤러 내부에서 직접 처리 — 코드 중복 발생
- 추천 여부: 강력 추천
- 사용자 확인 필요 여부: 불필요

## 4. 데이터베이스 구조 제안

### 4-1. 테이블 구성 (K-01=A, K-02=B 기준) `[AI 제안안]`

- 제안: `users`, `categories`, `plans` 3개 테이블. `plans.category_id`는 `categories.id` FK.
- 이유: 사용자별 카테고리 커스터마이징(K-02=B)과 다중 사용자(K-01=A)를 동시에 지원하는 최소 구조다.
- 대안: K-01=B(단일 사용자)이면 `users` 테이블 불필요. K-02=A(고정 카테고리)이면 `categories` 테이블을 시드 데이터로 대체 가능.
- 추천 여부: 추천 (K-01, K-02 결정 후 확정)
- 사용자 확인 필요 여부: 필수 (decision-needed.md K-01, K-02 참고)

### 4-2. 주요 컬럼 — plans 테이블 `[명세서 확정]`

- 제안: `id`, `user_id`(FK), `title`(필수), `due_date`(필수), `due_time`(선택), `display_date`(필수), `category_id`(FK), `priority`(높음/보통/낮음), `memo`(선택), `is_completed`, `created_at`, `updated_at`, `deleted_at`(soft delete용)
- 이유: 명세서에 정의된 필드를 모두 포함하며 soft delete(`deleted_at`)를 위한 컬럼을 추가한다.
- 대안: hard delete — 단순하지만 실수 복구 불가
- 추천 여부: 추천
- 사용자 확인 필요 여부: 권장 (soft delete 정책 확인)

### 4-3. 인덱스 전략 `[AI 제안안]`

- 제안: `plans(user_id)`, `plans(display_date)`, `plans(due_date)`, `plans(user_id, display_date)` 복합 인덱스
- 이유: 메인 페이지의 월간 캘린더 조회와 오늘 할 일 조회가 `user_id + display_date` 기준이므로 해당 복합 인덱스가 가장 빈번하게 사용된다.
- 대안: 인덱스 없음 — SQLite 소규모에서 허용되지만 데이터 증가 시 성능 저하
- 추천 여부: 추천
- 사용자 확인 필요 여부: 불필요

### 4-4. 마이그레이션 도구 `[AI 제안안]`

- 제안: Prisma Migrate (`prisma migrate dev` / `prisma migrate deploy`)
- 이유: 스키마 변경을 버전 관리하고, 팀 협업 시 DB 상태를 동기화한다.
- 대안: 수동 SQL 마이그레이션 파일 — 단순하지만 추적이 어려움
- 추천 여부: 강력 추천
- 사용자 확인 필요 여부: 불필요

## 5. 인증/인가 방식 제안

> `[사용자 결정 필요]` — K-01 결정에 따라 이 섹션 전체 채택 여부가 결정됩니다. decision-needed.md K-01 참고.

### 5-1. JWT 방식 `[AI 제안안]`

- 제안: Access Token(1시간, Authorization 헤더) + Refresh Token(7일, httpOnly 쿠키)
- 이유: Access Token을 짧게 유지해 탈취 위험을 줄이고, Refresh Token을 httpOnly 쿠키로 저장해 XSS로부터 보호한다.
- 대안: (A) 세션 기반(express-session + SQLite store) — 서버 상태 필요, 스케일 아웃 어려움 / (B) Access Token만 localStorage — 단순하지만 XSS 취약
- 추천 여부: 추천
- 사용자 확인 필요 여부: 권장

### 5-2. 비밀번호 해싱 `[AI 제안안]`

- 제안: bcrypt (cost factor 12)
- 이유: 업계 표준이며 cost factor 12는 보안성과 응답 속도의 균형점이다.
- 대안: argon2 — 메모리 하드 알고리즘으로 더 강력하지만 Node.js 네이티브 바인딩 필요
- 추천 여부: 추천
- 사용자 확인 필요 여부: 불필요

### 5-3. 인증 미들웨어 `[AI 제안안]`

- 제안: 모든 `/api` 경로에 `authMiddleware` 적용, `/api/auth/login`, `/api/auth/register`는 공개 경로로 예외 처리
- 이유: 기본 차단 후 예외 허용 방식이 보안 누락 위험이 낮다.
- 대안: 경로별 수동 적용 — 누락 위험
- 추천 여부: 강력 추천
- 사용자 확인 필요 여부: 불필요

## 6. 사용자 역할과 권한 제안

### 6-1. 초기 역할 설계 `[AI 제안안]`

- 제안: 단일 역할 `user` — 자신의 일정·카테고리만 CRUD 가능. 다른 사용자 데이터 접근 불가.
- 이유: PlanMate는 개인 일정 관리 서비스이므로 초기에는 단일 역할로 충분하다.
- 대안: `admin` 역할 추가 — 향후 확장 시 `role` 컬럼을 `users` 테이블에 추가해 대응 가능
- 추천 여부: 추천
- 사용자 확인 필요 여부: 불필요

### 6-2. 권한 매트릭스 `[AI 제안안]`

- 제안: 아래 표 기준으로 서비스 레이어에서 `plan.user_id === req.user.id` 검증 필수

  | 리소스 | 생성 | 조회 | 수정 | 삭제 |
  |---|---|---|---|---|
  | 본인 일정 | O | O | O | O |
  | 타인 일정 | X | X | X | X |

## 13. 날짜와 시간 처리 방식 제안

### 13-1. 날짜 포맷 표준화 `[AI 제안안]`

- 제안: API 입출력은 ISO 8601 형식 — 날짜 `YYYY-MM-DD`, 시간 `HH:mm`. DB(SQLite)는 TEXT 타입으로 ISO 형식 저장.
- 이유: SQLite에는 별도 DATE 타입이 없으므로 TEXT 저장이 표준이며, ISO 형식은 정렬·비교가 용이하다.
- 대안: UNIX timestamp 정수 저장 — 연산은 빠르지만 가독성 낮음
- 추천 여부: 강력 추천
- 사용자 확인 필요 여부: 불필요

### 13-2. 타임존 전략 `[AI 제안안]`

- 제안: KST(UTC+9) 고정. 서버와 클라이언트 모두 KST 기준으로 처리. `date-fns`의 `format`/`parseISO` 사용 시 로컬 타임존 주의.
- 이유: 대학생 대상 국내 서비스이므로 단일 타임존으로 충분하며, 복수 타임존 처리 비용이 불필요하다.
- 대안: UTC 저장 + 클라이언트 변환 — 글로벌 서비스 표준, 이 서비스엔 과함
- 추천 여부: 추천
- 사용자 확인 필요 여부: 불필요

### 13-3. D-Day 계산 위치 `[명세서 확정]`

- 제안: 클라이언트 사이드에서 `date-fns`의 `differenceInCalendarDays(due_date, today)`로 계산
- 이유: 명세서 D-Day 규칙이 단순하며 클라이언트 계산으로 충분. 서버 의존 없이 실시간 갱신.
- 대안: 서버 계산 포함 — 불필요한 서버 부담
- 추천 여부: 강력 추천
- 사용자 확인 필요 여부: 불필요

## 14. 에러 처리 방식 제안

### 14-1. 표준 에러 응답 형식 `[AI 제안안]`

- 제안: 모든 에러는 `{ success: false, error: { code: string, message: string, details?: any } }` 형식으로 반환
- 이유: 클라이언트가 에러 종류를 `code` 필드로 판단해 토스트 메시지 또는 폼 에러를 구분 처리 가능.
- 대안: HTTP 상태 코드만 반환 — 정보 부족, 클라이언트 처리 어려움
- 추천 여부: 강력 추천
- 사용자 확인 필요 여부: 불필요

### 14-2. HTTP 상태 코드 규칙 `[AI 제안안]`

- 제안:

  | 코드 | 상황 |
  |---|---|
  | 400 | 잘못된 요청 형식 |
  | 401 | 인증 실패 (토큰 없음/만료) |
  | 403 | 권한 없음 (타인 리소스 접근) |
  | 404 | 리소스 없음 |
  | 409 | 충돌 (중복 이메일 등) |
  | 422 | 유효성 검증 실패 |
  | 500 | 서버 내부 오류 |

- 이유: 일관된 코드 사용으로 클라이언트 분기 처리를 단순화한다.
- 대안: 모든 에러를 200으로 반환 후 body 분기 — 안티패턴
- 추천 여부: 강력 추천
- 사용자 확인 필요 여부: 불필요

### 14-3. 클라이언트 에러 UX `[AI 제안안]`

- 제안: 전역 에러는 토스트 알림(상단 우측), 폼 필드 에러는 인라인 메시지, 401 수신 시 자동 Refresh Token 시도 후 실패 시 `/login` 리디렉션
- 이유: 에러 유형에 따라 적절한 위치에 표시해 사용자 혼란을 줄인다.
- 대안: alert() 사용 — 단순하지만 UX 저하
- 추천 여부: 강력 추천
- 사용자 확인 필요 여부: 불필요

## 15. 입력 검증 방식 제안

- 대안: 프론트/백 각각 별도 검증 — 동기화 누락 위험
- 추천 여부: 강력 추천
- 사용자 확인 필요 여부: 불필요

### 15-2. 주요 검증 제약 `[명세서 확정 + AI 제안안]`

## 18. AI가 제안한 가정 사항

> `[AI 제안안]` — 아래 가정들은 명세서에 명시되지 않아 AI가 합리적 판단으로 채택한 내용입니다. 동의 또는 거부 의사를 알려주시면 반영합니다.

| 번호 | 가정 사항 | 근거 |
|---|---|---|
| A-01 | 서비스는 다중 사용자를 지원한다 (K-01=A 기준) | 디자인에 로그인/회원가입/프로필 존재 |
| A-02 | 타임존은 KST(UTC+9) 단일 사용 | 국내 대학생 대상 서비스 |
| A-03 | 삭제는 soft delete (`deleted_at`) 방식 | 실수 복구, 데이터 추적 필요 |
| A-04 | 기본 키는 정수 자동 증가(INTEGER PRIMARY KEY) | SQLite 표준, 단순성 |
| A-05 | 이메일은 RFC 5322 단순화 정규식으로 검증 | 완전한 RFC 구현은 과함 |
| A-06 | 비밀번호는 영문+숫자 포함 8자 이상 | 일반적 보안 기준 |
| A-07 | 아바타 이미지는 로컬 파일 시스템에 저장 | MVP 범위, 외부 스토리지 불필요 |
| A-08 | 월간 캘린더 조회는 `display_date` 기준으로 서버 필터링 | 효율적 쿼리 |
| A-09 | 검색 범위는 일정 제목 + 메모 | 명세서 미명시, 자연스러운 범위 |
| A-10 | 초기 5개 카테고리는 계정 생성 시 자동 시드 (K-02=B 기준) | 커스터마이징과 기본값 양립 |
| A-11 | D-Day 계산은 클라이언트에서 수행 | 서버 부담 없이 실시간 갱신 |
| A-12 | 다크 모드는 MVP 범위에서 제외 | 명세서 미명시 |
| A-13 | API 버전 prefix는 `/api/v1` 사용 | 향후 버전 호환성 |
| A-14 | 페이지네이션 기본 limit은 50개 | 개인 일정 수준 충분 |
