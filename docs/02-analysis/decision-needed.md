### K-01. 다중 사용자 지원 여부

- **영향 범위:** 인증 시스템 전체, JWT 구현, `users` 테이블, 모든 API의 `user_id` 필터링, 프로필 페이지, Protected Routes
- **관련 충돌:** C-01 (로그인/회원가입 — 명세서 없음, 디자인 있음)
- **선택지:**

  | | 선택지 | 설명 |
  |---|---|---|
  | A | 다중 사용자 (권장) | 로그인·회원가입·JWT 인증 포함. 디자인 기준. |
  | B | 단일 사용자 | 인증 없음. 명세서 범위만 구현. 앱 단일 사용. |

- **AI 권장안: A** — 디자인에 로그인·회원가입·프로필이 모두 구현되어 있으며, 향후 다른 사용자 추가 시 재구조화 비용이 크다. 초기부터 다중 사용자 구조를 갖추는 것이 유리하다.
- **우선순위:** 최우선 (이 결정이 나야 Phase 1 개발 방향 확정 가능)

---

### K-02. 카테고리 커스터마이징 허용 여부

- **영향 범위:** `categories` 테이블 구조, 카테고리 CRUD API, ER 모델, 프로필/설정 UI
- **관련 충돌:** C-03 (고정 5개 — 명세서, 사용자 추가·수정·삭제 — 디자인)
- **선택지:**

  | | 선택지 | 설명 |
  |---|---|---|
  | A | 고정 5개 카테고리 | 미팅·과제·시험·개인 일정·약속 고정. 사용자 변경 불가. 명세서 기준. |
  | B | 사용자 커스터마이징 (권장) | `categories` 테이블에 `user_id` FK. CRUD 가능. 초기 5개 자동 생성. |

- **AI 권장안: B** — 디자인에 커스터마이징 UI가 존재하며, 사용자마다 다른 수업·과제 이름을 쓰는 대학생 환경에서 유연성이 높다. 단, K-09(삭제 시 처리) 함께 결정 필요.
- **우선순위:** 최우선 (DB 스키마 확정에 필수)

---

### K-03. 카테고리 색상 정책

- **영향 범위:** Tailwind 색상 토큰 정의, DB `categories.color` 컬럼 타입, PlanCard·CategoryChip 컴포넌트 렌더링 로직
- **관련 충돌:** C-04 (컬러풀 5색 — 명세서, 그레이스케일 12색 — 디자인)
- **선택지:**

  | | 선택지 | 설명 |
  |---|---|---|
  | A | 컬러풀 5색 고정 | 보라·파랑·빨강·초록·주황. 명세서 기준. 직관적 구분. |
  | B | 그레이스케일 12색 | Serene Productivity 디자인 시스템 기준. 모노크로매틱. |
  | C | 사용자 지정 색상 | K-02=B 시 사용자가 색상 선택 (hex 또는 팔레트). |

- **AI 권장안: A 또는 C** — 명세서의 컬러풀 5색이 카테고리 시각 구분에 효과적이다. K-02=B 선택 시 C안(사용자 지정)이 일관성 있다. 그레이스케일(B)은 카테고리 구분이 어렵다.
- **우선순위:** 높음

---

### K-04. 오늘 할 일 정렬 1순위

- **영향 범위:** 백엔드 `GET /api/v1/plans` 정렬 쿼리, 클라이언트 정렬 유틸 함수
- **관련 충돌:** C-08 (명세서 내 모순 — 5.3절: 중요도 우선, 8.1절: 마감시간 우선)
- **선택지:**

  | | 선택지 | 설명 |
  |---|---|---|
  | A | 중요도 우선 → 마감시간 보조 | 높음 > 보통 > 낮음, 같은 중요도는 마감시간 순. 명세서 5.3절 기준. |
  | B | 마감시간 우선 → 중요도 보조 | 가장 빠른 마감시간 순, 같은 시간은 중요도 순. 명세서 8.1절 기준. |

- **AI 권장안: A** — "할 일" 목록에서는 중요도가 먼저 눈에 들어오는 것이 자연스럽다. 마감시간이 없는 일정(due_time=null)이 존재하므로 중요도를 1순위로 삼는 것이 더 안정적이다.
- **우선순위:** 높음

---

### K-05. 메인 페이지 섹션 순서

- **영향 범위:** 메인 페이지(`/`) 컴포넌트 배치 순서, 스크롤 UX
- **관련 충돌:** C-05 (명세서: 캘린더→오늘→주간, 디자인: 캘린더→주간→오늘)
- **선택지:**

  | | 선택지 | 설명 |
  |---|---|---|
  | A | 캘린더 → 오늘 할 일 → 주간 할 일 바 | 명세서 순서. 오늘 일정 우선 노출. |
  | B | 캘린더 → 주간 할 일 바 → 오늘 할 일 | 디자인 순서. 주간 개요를 먼저 파악. |

- **AI 권장안: B** — 주간 할 일 바는 요약 정보로 캘린더와 연속성이 있으며, 오늘 할 일은 상세 목록이므로 아래에 두는 것이 정보 계층상 자연스럽다. 디자인 시안에 이미 검토된 배치.
- **우선순위:** 보통 (레이아웃만 영향, 기능 구현과 독립적)

---

### K-06. 프로필 페이지 포함 여부

- **영향 범위:** `/profile` 경로, `GET/PATCH /api/v1/profile`, 아바타 업로드 API, `users` 테이블 `nickname`·`avatar_url` 컬럼
- **관련 충돌:** C-02 (프로필 페이지 — 명세서 없음, 디자인 있음)
- **선택지:**

  | | 선택지 | 설명 |
  |---|---|---|
  | A | 포함 (권장) | 닉네임·비밀번호 변경·아바타 업로드. 디자인 기준. K-01=A 전제. |
  | B | 제외 | 프로필 페이지·API 전체 제외. 명세서 범위 준수. |

- **AI 권장안: A** — K-01=A(다중 사용자) 선택 시 계정 관리 페이지는 자연스러운 구성이다. 디자인이 이미 준비되어 있어 추가 설계 비용이 낮다.
- **우선순위:** 높음 (K-01=A 전제)

---

### K-07. "당일날 알려주기" 처리 방식

- **영향 범위:** 알림 서브시스템 도입 여부, `plans.remind` 컬럼, 브라우저 Notification API 또는 이메일 발송 시스템
- **관련 충돌:** C-06 (알림 기능 — 명세서 제외, 디자인 체크박스 존재)
- **선택지:**

  | | 선택지 | 설명 |
  |---|---|---|
  | A | 완전 제외 | 필드 자체 제거. 명세서 기준. |
  | B | UI만 포함, 기능 비활성 | 체크박스는 표시하되 실제 알림 미발송. 디자인 유지, 기능 제외. |
  | C | 브라우저 알림 구현 | Web Notifications API 사용. 탭이 열려 있어야 작동. |

- **AI 권장안: B** — 알림 서브시스템(백엔드 스케줄러, 이메일/푸시 발송)은 MVP 범위를 크게 벗어난다. 체크박스 UI는 유지하되 `is_remind` 컬럼만 저장하고 실제 발송은 향후 단계로 미루는 것이 현실적이다.
- **우선순위:** 높음 (DB 컬럼 포함 여부에 영향)

---

### K-08. 일정 상세 표시 방식

- **영향 범위:** 라우팅 구조(`/plans/:id` 경로 존재 여부), React Router 설정, UX 흐름
- **관련 충돌:** 해당 없음 (명세서·디자인 모두 명시 없음)
- **선택지:**

  | | 선택지 | 설명 |
  |---|---|---|
  | A | 독립 페이지 `/plans/:id` | URL로 직접 접근 가능. 뒤로 가기 자연스러움. |
  | B | 모달 (권장) | 메인 페이지 위에 오버레이. 캘린더 컨텍스트 유지. URL은 모달 열린 상태 반영 가능. |

- **AI 권장안: B** — 일정 관리 앱 특성상 캘린더를 보면서 상세 내용을 확인하는 흐름이 자연스럽다. URL은 `?planId=123` 쿼리 파라미터로 공유 가능하게 구현하면 두 가지 장점을 모두 취할 수 있다.
- **우선순위:** 보통

---

### K-09. 카테고리 삭제 시 연결 일정 처리

> K-02=A(고정 카테고리) 선택 시 이 결정은 불필요합니다.

- **영향 범위:** `DELETE /api/v1/categories/:id` API 로직, DB 무결성 정책(`plans.category_id` FK 처리)
- **관련 충돌:** 해당 없음 (K-02=B 채택 시 발생하는 파생 결정)
- **선택지:**

  | | 선택지 | 설명 |
  |---|---|---|
  | A | 삭제 차단 | 연결된 일정이 있으면 카테고리 삭제 불가. 409 Conflict 반환. |
  | B | 연결 일정 null 처리 (권장) | 삭제 시 `plans.category_id`를 null로 변경. 일정은 유지. |
  | C | 연결 일정 함께 삭제 | CASCADE DELETE. 데이터 손실 위험. |

- **AI 권장안: B** — 일정 데이터 유실 없이 카테고리를 자유롭게 관리할 수 있다. 카테고리 없는 일정은 "미분류"로 표시하면 UX상 자연스럽다. C안은 데이터 손실 위험으로 비추천.
- **우선순위:** 보통 (K-02=B 결정 시에만 해당)

---

### K-10. display_date 의미 확정

- **영향 범위:** `plans.display_date` 컬럼 의미 정의, 오늘 할 일 조회 쿼리 기준, 캘린더 표시 기준 날짜
- **관련 충돌:** 해당 없음 (명세서에 "오늘 할 일 표시일"로만 명시, 구체적 의미 불명확)
- **선택지:**

  | | 선택지 | 설명 |
  |---|---|---|
  | A | due_date와 동일 (권장) | 마감일에 해당 일정을 표시. 별도 입력 없이 due_date 자동 복사. |
  | B | 사용자가 직접 입력 | "이 일정을 언제 할 것인가"를 별도 지정. due_date와 다를 수 있음. |

- **배경:** 명세서는 `display_date`를 "오늘 할 일 표시일"로 정의하며 필수 필드로 지정. 예: 마감이 금요일인 과제를 화요일부터 표시하고 싶을 때 `display_date=화요일`.
- **AI 권장안: B** — 명세서의 정의대로 `display_date`는 "오늘 할 일에 나타날 날짜"로 해석하는 것이 자연스럽다. A안은 `display_date` 존재 의미가 없어진다. 단, 등록 폼에서 `display_date` 입력 UI(기본값: due_date)를 명시적으로 제공해야 혼란을 줄일 수 있다.
- **우선순위:** 높음 (오늘 할 일 섹션 구현 전 확정 필요)
