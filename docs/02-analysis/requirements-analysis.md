# PlanMate 요구사항 분석서

> **문서 목적:** 기능명세서와 디자인 레퍼런스를 토대로 개발 가능한 PRD(프론트엔드+백엔드)의 기반을 마련하기 위한 분석 문서입니다.
> **분류 라벨 기준:**
> - `[확정]` — 기능명세서에 명시된 항목
> - `[AI 보완]` — 일반 웹 시스템 개발에 필수적이지만 명세서에 없는 항목
> - `[AI 제안]` — 권장하지만 최종 결정은 사용자가 필요한 항목
> - `[사용자 결정 필요]` — 충돌하거나 모호하여 반드시 사용자 답변이 필요한 항목

## 1. 서비스 개요

| 항목 | 내용 | 분류 |
|---|---|---|
| 서비스명 | PlanMate | `[확정]` |
| 서비스 유형 | 웹 기반 일정·과제 관리 서비스 | `[확정]` |
| 대상 사용자층 | 대학생 | `[확정]` |
| 핵심 콘셉트 | 월간 캘린더 중심의 과제·시험·미팅·약속·개인 일정 통합 관리 | `[확정]` |
| 디자인 철학 | 조용한 집중(quiet focus), 미니멀리즘, 모노크로매틱 "Serene Productivity" | `[AI 보완]` |
| 기술 스택 (프론트엔드) | React (TypeScript) + TailwindCSS | `[확정]` |
| 기술 스택 (백엔드) | Node.js (TypeScript) | `[확정]` |
| 데이터베이스 | SQLite | `[확정]` |
| 초기 제외 기능 | 알림 기능, AI 추천 기능, 과제 진행률 | `[확정]` |
| 향후 확장 기능 | AI 자동 분류, AI 우선순위 추천, AI 하루 계획, 알림, 반복 일정, 팀플 공유, 학기별 관리 | `[확정]` |

**서비스 한 줄 요약:** PlanMate는 대학생이 과제·시험·미팅 등 학업 일정을 월간 캘린더와 오늘 할 일 목록으로 직관적으로 관리할 수 있는 웹 서비스입니다.

## 2. 대상 사용자

| 사용자 유형 | 설명 | 분류 |
|---|---|---|
| 주 사용자 | 대학생 — 과제·시험·미팅·약속·개인 일정을 복합적으로 관리해야 하는 사람 | `[확정]` |
| 사용 환경 | 웹 브라우저 (모바일 반응형 여부 미명시) | `[사용자 결정 필요]` |
| 계정 방식 | 이메일+비밀번호 기반 회원가입/로그인 (디자인 확인) | `[AI 보완]` |

**사용자 니즈 요약 (추론):**
- `[AI 보완]` 여러 과목과 활동의 마감일을 한눈에 파악하고 싶다.
- `[AI 보완]` 오늘 해야 할 일의 우선순위를 빠르게 확인하고 싶다.
- `[AI 보완]` 완료한 일정을 기록으로 남기고 싶다 (삭제하지 않는 완료 처리).
- `[확정]` 카테고리(과제/시험/미팅/약속/개인 일정)로 일정을 분류하고 싶다.

## 10. 날짜와 시간 관련 규칙

| 규칙 | 내용 | 분류 |
|---|---|---|
| 마감일 (due_date) | 필수 입력. 날짜 선택 UI (date picker) | `[확정]` |
| 마감 시간 (due_time) | 선택 입력. 시간 선택 UI (time picker) | `[확정]` |
| 오늘 할 일 표시 날짜 (display_date) | 마감일과 별개로 필수 입력. "오늘 할 일" 목록에 나타나는 날짜 기준 | `[확정]` |
| D-Day 계산 기준 | due_date 기준. 오늘 = D-Day, 내일 = D-1, 3일 후 = D-3, 지났으면 "마감 지남", 4일 이상 남으면 날짜만 표시 | `[확정]` |
| "오늘 할 일" 노출 기준 | display_date가 오늘인 일정 | `[확정]` |
| 타임존 | 미명시 (한국 KST 가정 권장) | `[AI 보완]` KST (UTC+9) 기준 권장 |
| 날짜 형식 | 디자인에서 mm/dd/yyyy 확인. 표시는 한국어 형식(2024년 10월 23일)도 혼용 | `[사용자 결정 필요]` |
| 주간 일정 바 기준 | 월~일 (display_date 또는 due_date 기준?) | `[사용자 결정 필요]` |

> `[사용자 결정 필요]` "오늘 할 일" 기준이 `display_date`인지 `due_date`인지를 명확히 해야 합니다. 현재 명세서 해석 상 `display_date` 기준으로 판단하나, 주간 일정 바도 동일 기준인지 확인 필요.

> `[사용자 결정 필요]` `display_date`의 의미: 사용자가 "이 날 이 할 일을 처리하겠다"는 의도를 표현하는 날짜인지, 아니면 단순 캘린더 표시 날짜인지 명확화 필요.

## 25. AI가 시스템 설계로 보완할 수 있는 부분

| 항목 | AI 보완 내용 | 근거 |
|---|---|---|
| 인증 시스템 | JWT 기반 이메일+비밀번호 인증, bcrypt 해싱, 인증 미들웨어 | 일반 웹 시스템 표준 |
| 비밀번호 정책 | 영문+숫자 포함 8자 이상 (디자인 02 확인) | 디자인 레퍼런스 |
| API 에러 응답 구조 | `{ success, message, data, error }` 일관된 형태 | 표준 REST 설계 |
| 검색 방식 | SQL LIKE `%keyword%` 부분 일치, 대소문자 무시 | 사용자 편의 |
| 다중 필터 AND 조건 | 카테고리+중요도+완료 여부 동시 필터 AND 적용 | 일반적 필터 동작 |
| 타임존 | 서버 KST(UTC+9) 기준 처리, 클라이언트도 동일 | 한국 서비스 표준 |
| 토큰 전략 | Access Token(1시간) + Refresh Token(7일) | 보안+UX 균형 |
| 입력 최대 길이 | 제목 100자, 메모 500자, 닉네임 20자 | 일반적 제약 |
| 빈 상태(Empty State) UI | "일정이 없습니다", "검색 결과가 없습니다" 표시 | 일반 UX 패턴 |
| 로딩 상태 | 버튼 비활성화 + 스피너 (API 호출 중) | 일반 UX 패턴 |
| 세션 만료 처리 | 만료 시 로그인 페이지 자동 리다이렉트 | 보안 표준 |
| 날짜 포맷 통일 | ISO 8601 (YYYY-MM-DD) API 전송, 한국어 표시 변환 | 국제 표준 |
| display_date 모델 | 사용자가 "이 날 처리하겠다"고 지정하는 의도적 날짜 | 명세서 5.2 해석 |
| 이미지 저장 | 초기에는 로컬 서버 저장 (`/uploads`) | SQLite 스택에 적합 |
| D-Day 계산 위치 | 클라이언트 사이드 실시간 계산 (today 기준) | 성능 최적화 |
